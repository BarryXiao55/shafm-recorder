# 网络电台直播（以上海新闻广播 FM93.4 / AM990 为例）能否保存、如何落地为本地音频文件

调研时间：2026-11-14（本机实测 + 公开资料核查）

---

## 一句话结论

**实时网络电台本身不是一个「文件」，而是一条不会结束的音频流；服务器侧不存在一个完整的 .mp3 让你下载，必须由你在收听端「拉流 → 重新封装/转码 → 写入本地文件」才能得到可保存的声音文件。** 唯一例外是官方的「回听/点播」节目，那些已经是完整音频文件，但被平台限制在 App 内离线播放，无法导出成硬盘上的通用文件。

---

## 一、问题 1：是文件，还是要处理成文件？

### 1.1 三种形态必须分开看

| 形态 | 本质 | 服务器侧有没有完整文件 | 能否「另存为」得到音频 | 本次 FM990 的对应情况 |
|---|---|---|---|---|
| 直播流（ICY / Icecast / SHOUTcast 类） | 一个永不结束的 HTTP 响应，`Transfer-Encoding: chunked`，无 `Content-Length` | ❌ 没有 | ❌ 浏览器另存为只能存到播放页/无限增长的裸数据 | ✅ **本次实测就是这种：MP3 长连接流** |
| 直播流（HLS / DASH 类） | 播放列表 `.m3u8` + 一堆 6~10 秒分片 `.ts`/`.m4s`，滚动更新、旧分片会被删 | ⚠️ 只有碎片，没有整体 | ❌ 需边下边拼接；可能有 AES-128 加密与 token 鉴权 | SMG 早年的 `l3.smgtech.net/AppName/990.m3u8` 属此类，**域名现已不存在** |
| 回听 / 点播节目 | 标准完整音频文件（有 Content-Length、时长、元数据） | ✅ 有 | ✅ 技术上是真正的文件 | 阿基米德 App 的「音像馆/往期/离线缓存」，**仅 App 内播放、不支持导出** |

### 1.2 FM990 本机实测结果（2026-11-14）

从公开电台目录（radio-browser.info，记录最后校验时间 2026-11-12）拿到两条直播源，我用 HTTP 请求实测：

| 项目 | 实测值 |
|---|---|
| 流地址 A | `http://lhttp.qingting.fm/live/270/64k.mp3` |
| 流地址 B（推荐，HTTPS） | `https://lhttp-hw.qtfm.cn/live/270/64k.mp3` |
| HTTP 状态 / 类型 | `200 OK` / `Content-Type: audio/mpeg` |
| 传输方式 | `Transfer-Encoding: chunked`、`Connection: keep-alive`、`Cache-Control: no-store` |
| ICY 元数据 | `icy-metadata: 1`（即典型的 SHOUTcast/Icecast 长连接流，曲目标题夹在音频里） |
| 短时实测（5 s / 20 s） | 105 KB / 223 KB，均值 21 KB/s / 11.2 KB/s —— **含开播一次性补推的约 60 KB 缓冲，不是稳态码率** |
| 稳态复测（60 s / 45 s） | 547 KB / 463 KB；用 20 s 与 60 s 两点求斜率得 **≈ 8.1 KB/s ≈ 65 kbps**，与地址里的 `64k` 吻合（chunked 发送非严格匀速，故短样本偏高） |
| 5 秒后是否结束 | 否，持续吐数据直到我主动超时断开（curl 报 timeout 28，符合「永不结束」特征） |
| 旧 HLS 地址 `l3.smgtech.net/AppName/990.m3u8` | DNS 返回 **Non-existent domain**，已失效 |

> 结论：这条流是「一条无限长的 MP3 字节流」，没有总时长、没有索引。直接下载存盘虽然能得到一个可播放的 mp3（字节本身就是音频帧），但开头会带一小段非音频前导，且缺少时长索引、不便拖动进度条。正确做法是 **字节原样写盘 + 跳过前导做帧对齐 + 按时间分段**，或让 ffmpeg 做无损封装（`-c copy`）。

### 1.2.1 音频格式复核（2026-11-14 22:00，原型开发时补做）

用 MPEG 帧解析器对录出的字节做连续帧校验：**MPEG-1 Layer III / 64 kbps / 44.1 kHz 标准 MP3 裸流**，从首个帧同步起连续 400+ 帧自洽（帧长 209 字节）；开头有 30~180 字节非音频前导。跳过前导并做帧对齐后，文件从第一个字节就是纯 MP3 帧（`FF FB…`），任何播放器可直接解码。

由此确定「最高保真、不失真」的正确做法：

| 要点 | 结论 |
|---|---|
| 零二次损失 | `-c copy` 或字节原样写盘 = 不解码、不重编码、不重采样、不动音量，录到的就是电台发出的原始码流 |
| 音质天花板 | 源流本身 64 kbps 有损；128k / 32k 路径实测均 404，没有更高码率公开流 |
| 会劣化的操作 | 转 MP3/AAC、改码率、重采样、经声卡环回录音，都会再损一次或引入模拟噪声 |
| 帧对齐 | 跳过开头非音频字节、每个分段从完整 MP3 帧开始，消除开头杂音；不丢任何音频数据 |
| 硬件路线 | 若追求超越网络流的音质，只能改用 FM93.4 射频接收 + USB 声卡 Line-in 录 WAV/FLAC（但受射频与声卡链路影响，且已是另一条链路） |

> 配套可运行原型见 `radio-recorder/`：已内置流格式自检、帧对齐、零重编码录制与按小时分段。

### 1.3 关于「官方回听」这条捷径

阿基米德 FM（SMG 官方音频平台，上海新闻广播的网络直播/回听主渠道）提供「往期节目回听」「离线缓存」，这些是完整音频文件。**但公开资料明确：下载音频仅限 App 内离线播放，不支持导出到本地其他播放器。** 因此只要目标是「本地硬盘上一个通用的 .mp3/.m4a」，仍然得自己录。

## 二、问题 2：怎样处理、保存成本地硬盘文件

### 2.1 处理链路（四个动作，缺一不可）

```
找到真实流地址 → 工具持续拉流 → 重新封装(-c copy) 或转码 → 写入本地文件（分段/命名/定时/清理）
```

- **重新封装（remux，`-c copy`）**：只换「容器」，音频帧原样拷贝，**零音质损失、CPU 几乎为零**，是首选。
- **转码（`-c:a libmp3lame` / `aac`）**：重新编码，有二次损失，但兼容性、进度条、码率统一更可控。
- 建议：先 `-c copy` 落地原始流，需要给手机/剪辑软件用时再离线转码一次。

### 2.2 方案对比（按推荐度）

| 方案 | 做法 | 是否需转码 | 优点 | 缺点 / 适用边界 |
|---|---|---|---|---|
| ⭐ **A. FFmpeg 命令行** | 直接对流地址录制 | 可选（推荐 copy） | 零损失、可定时/分段/重连/无人值守、一条命令搞定 | 需装 ffmpeg、需拿真实流地址 |
| **B. VLC 图形界面** | 媒体 → 打开网络串流 → 转换/保存 → 选 Audio-MP3 配置 → 指定目标文件 | 默认转码 | 零命令行、最直观 | 长时间录制易中断；不适合 7×24 自动化 |
| **C. yt-dlp / streamlink** | `yt-dlp <流地址>` 或 `streamlink <流地址> best -o out.mp3` | 通常 copy | 对部分 HLS 流开箱即用 | 对纯 ICY 流支持不稳定 |
| **D. 声卡环回录音** | Audacity(WASAPI loopback) / OBS / VB-Cable 录「系统声音」 | 必然重编码 | **任何播放器能出声就能录**，流地址拿不到、有 DRM 时的兜底 | 只能 1:1 实时、受系统混音/音量/设备切换影响、需人工值守 |
| **E. 硬件射频路线** | FM 收音头 / RTL-SDR 接收 FM93.4 → 声卡 Line-in 录入 | 必然重编码 | 完全不依赖网络与平台 | 音质受射频与声卡影响，硬件活儿多 |

> 对你手上那块 Raspberry Pi **Pico（RP2040）**：它没有网络接口、没有大容量存储，做不了这件事；要做 7×24 录制盒子建议换成树莓派 4/5 或一台常开的 Windows 小主机跑 FFmpeg（CPU 占用极低，老机器也够）。

### 2.3 第一步：装 FFmpeg（本机检查结果为「未安装」）

```powershell
winget install --id Gyan.FFmpeg -e
```
或手动：到 `https://github.com/BtbN/FFmpeg-Builds/releases` 下载 Windows 版 zip，解压到 `C:\ffmpeg\bin`，把该目录加入 PATH。`ffmpeg -version` 能打印版本即成功。

### 2.4 直接可用的命令（本次实测的 FM990 流）

**① 录固定时长（例如《990早新闻》1 小时）**

```powershell
$ts = Get-Date -Format "yyyyMMdd_HHmm"
ffmpeg -hide_banner -loglevel warning `
  -reconnect 1 -reconnect_streamed 1 -reconnect_at_eof 1 -reconnect_delay_max 10 `
  -rw_timeout 10000000 `
  -i "https://lhttp-hw.qtfm.cn/live/270/64k.mp3" `
  -t 3600 -vn -c:a copy "D:\Radio\FM990\990_$ts.mp3"
```

**② 无人值守长期录制：按小时自动切文件 + 断线自动重连**

见同目录的 `record_fm990.bat`，双击即可运行，核心参数：

```
-reconnect 1 -reconnect_streamed 1 -reconnect_at_eof 1 -reconnect_delay_max 10
-i <流地址> -c:a copy
-f segment -segment_time 3600 -reset_timestamps 1 -strftime 1
"D:\Radio\FM990\FM990_%%Y%%m%%d_%%H%%M%%S.mp3"
```

参数说明：

| 参数 | 作用 |
|---|---|
| `-reconnect*` / `-rw_timeout` | 网络抖动、服务器重启时自动重连（放在 `-i` **之前**才生效） |
| `-c:a copy` | 原样拷贝 MP3 帧，不重新编码、不损音质、CPU≈0 |
| `-f segment -segment_time 3600` | 每 1 小时切一个文件；单个文件损坏只丢这一段 |
| `-strftime 1` + `%%Y%%m%%d...` | 文件名带时间戳（.bat 中 `%` 必须写成 `%%`） |
| 外层 `:loop ... goto loop` | ffmpeg 万一退出，10 秒后自动重启，保证 7×24 |

**③ 若换成 HLS（`.m3u8`）源**

```powershell
# 最稳：直接把分片拼成 TS/MKV，避免封装不兼容
ffmpeg -i "<...>.m3u8" -c copy "D:\Radio\FM990\990.ts"

# 想要 m4a/mp4 容器（AAC in TS 需加 bitstream filter）
ffmpeg -i "<...>.m3u8" -c copy -bsf:a aac_adtstoasc -movflags +faststart "D:\Radio\FM990\990.m4a"
```

**④ 事后想要兼容性更好的 MP3（二次转码，可选）**

```powershell
ffmpeg -i "990.ts" -vn -c:a libmp3lame -b:a 64k -ar 44100 "990.mp3"
```

### 2.5 怎么自己找流地址（地址会变，这才是长期可靠的方法）

1. 打开官方收听页（如阿基米德 / SMG 频率页），按 `F12` → `Network`（网络）。
2. 过滤框输入 `m3u8|mp3|aac|ts|m4s`，点播放，看新增请求。
3. 复制那个 `Content-Type: audio/mpeg` 或 `.m3u8` 的 Request URL，先丢进 VLC「打开网络串流」验证能出声。
4. 再把该 URL 填进脚本的 `URL=` 变量。
5. 若地址带 token / 签名 / 加密，说明平台做了授权控制 —— 请使用官方允许的收听方式，不要绕过鉴权或 DRM。

### 2.6 定时录制（按节目单，不 24 小时全录）

Windows「任务计划程序」→ 创建基本任务 → 每天 06:00 → 启动程序 `ffmpeg.exe`，参数即 ① 的命令（或写个 PowerShell 脚本作为入口）。只录目标时段能省掉 90% 以上存储。

### 2.7 存储容量估算（按 `-c copy` 原码率，稳态 ≈ 64 kbps）

**结论：连续录 24 小时 ≈ 691 MB（0.69 GB，Windows 显示约 659 MiB）；按小时分段即 24 个文件、每个约 28.8 MB。**

推算：稳态 64 kbps = 8,000 B/s → `8000 × 86400 s = 691,200,000 B ≈ 691 MB`。开播时服务器会一次性补推约 60 KB 缓冲，可忽略；`-c copy` 不重新编码，文件体积≈流字节数（MP3 帧原样拷贝，封装开销 <0.1%）。

| 录制策略 / 码率 | 1 小时 | 24 小时（1 天） | 30 天 | 1 年 |
|---|---|---|---|---|
| **FM990 现流 64 kbps，24 h 全录（本次实测对象）** | **28.8 MB** | **691 MB ≈ 0.69 GB** | **20.7 GB** | **252 GB** |
| 64 kbps，每天只录 1 h（早新闻） | 28.8 MB | 28.8 MB | 0.86 GB | 10.5 GB |
| 64 kbps，每天 6 h | 28.8 MB | 173 MB | 5.2 GB | 63 GB |
| 96 kbps 源，24 h 全录 | 43.2 MB | 1.04 GB | 31 GB | 378 GB |
| 128 kbps 源 / 重编码，24 h 全录 | 57.6 MB | 1.38 GB | 41.5 GB | 504 GB |

> 单位说明：表中用十进制（1 GB = 1000 MB）；Windows 资源管理器按二进制显示，691 MB ≈ **659 MiB**。NTFS 4 KB 簇下 24 个分段文件最多多占约 100 KB，可忽略。

影响因素：

- `-c copy` 与 `-b:a 64k` 重编码在 64 kbps 下体积基本一致；若转码把码率设成 128 kbps，直接翻倍到 1.38 GB/天。
- 断线重连会留下空白时段，实际只会**小于**上述值，不会更大。
- HLS 分片拼接多带一些 TS 封装开销（通常 +2%~5%）；AES-128 加密不增加体积。
- 单文件 vs 按小时分段：总量相同，分段只多几个文件簇的零头。

配套建议：

- 目录按日期分：`D:\Radio\FM990\2026\11\...`，文件名 `FM990_YYYYMMDD_HHMMSS.mp3`。
- 加保留策略（例如 PowerShell 定期删除 90 天前文件），否则一年 250 GB 会悄悄吃满盘。
- 分段录制还有个好处：录制中途断电/断网，只坏当前那 1 小时文件，前面的都完好。
- 用 `ffprobe -v error -show_entries format=duration,bit_rate -of default=nw=1 文件名.mp3` 抽查时长/码率是否正常。

### 2.8 常见坑

| 现象 | 处理 |
|---|---|
| 录了几分钟就自动停 | 直播源缓冲被追上；加 `-re` / `-rtbufsize 20M`，HLS 源尤其常见 |
| 文件能播但没有时长、不能拖进度 | `-c copy` 直写 MP3 流的正常表现；按小时分段即可，或用播放器扫描全文件生成索引（**不要为此重编码**，会引入二次损失） |
| 每隔几分钟有空隙 | HLS 源避免 `-c copy`，改转码 AAC/MP3；或提高网络缓存 |
| 录出来静音 | 先用 VLC 验证 URL 能出声；声卡环回方案要检查 WASAPI 输入设备与电平 |
| 地址突然失效 | 正常，第三方公开流常变（本次 SMG 旧 HLS 域名已注销）；按 2.5 重新抓，或改用官方渠道 |

## 三、合规边界（重要）

- 依据《中华人民共和国著作权法》**第二十四条第（一）项**：「为个人学习、研究或者欣赏，使用他人已经发表的作品」可不经许可、不付报酬，但**不得影响作品正常使用、不得不合理损害权利人合法权益**；第 47 条另赋予广播组织禁止未经许可录制、复制、信息网络传播其播放的广播的权利。
- 可做的：个人时移收听、私人存档、家庭内播放。
- 不要做：把录音剪辑成播客/上传网盘分享、公开传播、商业使用、转播，或绕过平台的 token / DRM / 会员鉴权。合理使用一旦跨出「个人」边界，就进入需要授权的范围。
- 优先使用官方渠道（阿基米德直播/回听）与平台允许的收听方式。

## 五、录制台应用 v2（无人值守加固，2026-11-14 22:25 GMT+8）

原型已迭代为可长期运行的本地应用，代码在 `radio-recorder/`，端口 `127.0.0.1:8787`，**零 npm 依赖**（Node 18+ 即可）。

### 架构

| 文件 | 职责 |
|---|---|
| `config.json` | 用户可见的录制参数（UI 编辑） |
| `runtime.json` | 节目单、保留策略、触发去重、崩溃恢复快照（原子写：tmp + rename） |
| `server.js` | HTTP 服务、ffmpeg 进程管理、内置直录引擎、两个后台 tick |
| `lib/scheduler.js` | 纯调度逻辑（无 I/O，可单测）：每天/工作日/周末/指定星期/仅一次 |
| `lib/storage.js` | 磁盘水位、MP3 帧健康校验、时长估算、保留清理（计算与执行分离） |
| `lib/runtime.js` | 持久化状态与按日落盘日志 `logs/YYYY-MM-DD.log` |
| `test/selftest.js` | 14 项模块自测，`node test/selftest.js` 可复跑 |

### 本次新增

- **定时节目单**：多任务、启停、编辑、快捷模板、按日去重（重启也不会重复触发）、5 分钟补触发窗口；手动/24h 任务在跑时节目单不抢占，UI 会显著提示。
- **存储与清理**：`fs.statfsSync` 磁盘水位条；保留天数 / 总量上限 / 剩余空间下限三种触发条件；**自动清理默认关闭**，手动清理必须先预览、再确认，且只允许删除预览列出的文件；正在写入与刚写完 90 秒内的文件永不删。
- **断点续录**：每 5 秒写一次运行快照，服务重启后自动按剩余时长续录并开新分段；中断期间的音频不伪造、被中断的分段文件保留完整。
- **稳定性**：写盘背压（磁盘慢时暂停 socket 而非堆积内存）、45 秒无数据判定假连接主动重连、分段改为在 **MP3 帧边界**精确切割（此前每个整点会丢几百字节）、重连去重。
- **可观测性**：日志按日落盘并可在 UI 回看历史；文件列表显示估算时长与「完整 / 疑似损坏 / 写入中」；`/api/probe` 仍做录前流格式自检。
- **开机自启**：`install-autostart.bat` / `uninstall-autostart.bat`，只在当前用户启动文件夹写一个静默 VBS 启动器，不改注册表、可随时撤销。

### 保真结论不变

`-c copy` / 字节原样写盘：不解码、不重编码、不重采样、不动音量。实测录出的文件经帧链校验为 `MPEG-1 Layer III / 64 kbps / 44100 Hz`，首字节即 MP3 帧，帧链连续；`inspectAudio` 按 `size × 8 / bitrate` 估算时长，实测 6.50 MiB → 853 秒，与实际录制时长吻合。

| 6 秒试录 | ffmpeg 47.1 KiB、内置引擎 102.5 KiB（内置含开播补推缓冲），两者首字节 `FF FB`、64 kbps / 44.1 kHz |

### 三个格式层面的关键修正

1. **关掉 ID3v2 头**：ffmpeg 的 mp3 muxer 默认在文件头写 `ID3`（`49 44 33`）。单文件用 `-id3v2_version 0`，分段用 `-segment_format_options id3v2_version=0`，输出回归纯 MP3 裸帧（首字节 `FF FB`），与内置引擎一致，按字节无损合并时不会夹带多余标签。
2. **分段弃用 `-strftime 1`**：实测 ffmpeg 9.0.2 下多个分段会算出**同一个时间戳文件名**，`-y` 导致后段覆盖前段（8 秒测试只剩 1 个文件）。改用 `%04d` 递增序号后，12 秒测试产出 4 个独立分段、全部 `FF FB` 开头。这是长时录制会丢数据的真实坑。
3. **ffmpeg 引擎上报当前文件名**：从 `-loglevel info` 的 `Opening 'xxx' for writing` 解析真实分段名（忽略含 `%` 的输出模板），使「正在写入的文件不可删」「活跃度/速率条」在 ffmpeg 引擎下同样生效。

### 运维功能

- **停止服务**：`POST /api/shutdown`（可选清除续录快照）＋顶栏按钮；`stop-service.bat` 改为先走 API 再兜底清进程；关 `start.bat` 窗口 / Ctrl+C 亦可。
- **文件删除**：`/api/files/delete` 支持 `names[]` 批量，返回逐文件成功/跳过原因；UI 提供「全选可删 / 删除选中 / 删除全部 / 清理测试文件」，正在写入的文件显示「停止后删」并先停对应任务。
- **一键自检**：`lib/selftest.js` 12 项（Node、24 项单元测试、ffmpeg、电台库、4 秒流探测、写盘、删除链路、无损合并、MP3 帧校验、EPG 缓存、磁盘水位、HTTP 自连通），实测 **12 通过 / 0 提醒 / 0 失败**，临时文件自动清理。
